# Crash-safe renames: commit the decision, journal the plan, roll forward

ADR-0003 mandates two-phase renames and that the database and filenames never disagree after an operation, but defers the mechanics to this ADR (SPEC §9). The hard part is that SQLite transactions and filesystem renames cannot share one atomic commit: a crash between "DB updated" and "files renamed" must still leave a Library that the app can deterministically repair.

## Decision

**The database commit is the single decision point, and it comes first.** Every operation that changes a pack's files (reorder, insert, delete, duplicate/move via Send to pack, replace, thumbnail changes) runs through one rename engine:

1. **Stage (optional, pre-commit).** New image files (Send-to-pack copies, imports, replacements) are copied into the pack folder under unique reserved temp names (`.spm-tmp-add-…`) and byte-verified against their sources. Nothing in the database references them yet; on any failure the staged temps are deleted and the operation aborts with no DB change.
2. **Commit the decision.** One SQLite transaction writes (a) a `rename_journal` row for the pack holding the full plan as JSON — an ordered list of steps `{from, to}`, where `to: null` means delete — and (b) the final row state (positions, file names, inserted/deleted stickers). After this commit the operation **must** complete; everything below is roll-forward.
3. **Phase 1 — vacate.** Every step's `from` file is renamed to a deterministic temp name `.spm-tmp-<step index>`. Files that keep their name are untouched. Absent `from` files (a Missing sticker's slot) are skipped. After phase 1 no original name that any step targets is occupied, so phase 2 can never collide — this is why two phases are needed even for a simple swap.
4. **Phase 2 — place.** In plan order, each temp is renamed to its `to` name, or unlinked for delete steps. Delete steps are ordered before the placements that reuse their names.
5. **Clear the journal.** A final small transaction deletes the journal row. The operation is complete.

**Recovery runs on pack open and manual refresh, before desync detection** (never on app start, matching SPEC §4; and, since SPM-25, each time the Pack list is shown, see the amendment below). It is idempotent roll-forward:

- *Journal present:* the journal records whether phase 1 completed (a `phase` flag written after the last vacate, before the first placement). If phase 1 is unconfirmed, pass A completes it for any step whose `from` still exists under its original name; once phase 1 is confirmed, pass A is skipped — a placement may already have legitimately re-occupied an original name (e.g. `002.png` is both a source and a target in a rotation). Pass B then completes phase 2 for any remaining temp (place or unlink), and the journal row is deleted. A crash at any point — mid-phase-1, mid-phase-2, or after phase 2 but before journal cleanup — replays to the same final state, because the committed DB already describes the finals and the journal says exactly which file becomes which. If both a step's `from` and its temp exist while phase 1 is unconfirmed, the folder was tampered with externally and recovery reports an error instead of guessing.
- *No journal:* any stray `.spm-tmp-*` files are leftovers of a crash during staging (step 1, before any commit). No committed state references them, so they are deleted. Originals are untouched.

**Send to pack across two packs** (SPEC §5) sequences two engine operations: copy+verify ALL selected stickers into the target (step 1), commit the target's append (steps 2–5), and only then — if "delete originals" was requested — run delete+renumber on the source pack. The packs are not jointly atomic, deliberately: a delete-phase failure leaves the copies safely committed and produces an explicit final-state report (what was copied, what was deleted, what remains); each pack's journal recovers independently on next open. Never silent loss.

**Pack folders are named after the Short Name** (owner decision, 2026-11-20: Short Names rarely change in Draft and are immutable once Live, and meaningful folder names help when dragging files into @Stickers). Short Names are therefore unique within the Library, case-insensitively (`COLLATE NOCASE UNIQUE`; NTFS folder names are case-insensitive, and Telegram short names are unique too), and Windows reserved device names (`con`, `prn`, `aux`, `nul`, `com0`–`com9`, `lpt0`–`lpt9`) are refused. Auto-derived names that collide get a numeric suffix (`cats`, `cats_2`, …); a typed name that is taken is refused.

**Pack creation, deletion, and Short Name edits** use the same commit-first ordering. Creation: insert the pack row, create its folder, commit — a committed pack always has its folder; a pre-commit crash leaves at most an empty orphan folder, which is harmless and adopted by the next pack of that name (no reconstruction, SPEC §3). Deletion: delete the rows (cascading stickers and journal), commit, then remove the folder; a failure or crash after the commit leaves a leftover folder reported to the user, never a DB row pointing at nothing. A Draft Short Name edit commits the new name together with a `folder_rename_from` marker holding the old folder name, then renames the folder, then clears the marker. Recovery (`settle_pack_folder`, on pack open and before any operation on the pack's files) rolls an interrupted rename forward: old folder present → rename it; only the new one present → the rename already happened, clear the marker; both present → modified outside the app, report instead of guessing. A rename that cannot happen right now (on Windows, typically the folder open in Explorer) keeps the committed edit and the marker; the next open or refresh retries it.

## Rejected alternatives

- **DB commit last (files first, then rows).** A crash after the renames but before the commit leaves the DB describing old names that no longer exist; every sticker reads as Missing and the true mapping is unrecoverable without a journal anyway. Commit-first makes the committed DB the truth that recovery rolls toward.
- **Self-describing temp names, no journal** (temp encodes the original name; recovery matches temps back to DB rows). Ambiguous under permutations: in a 001↔002 swap, a crash mid-phase-2 leaves `002.png` holding sticker 1's bytes while the DB still says sticker 2 lives at `002.png` — matching by original name restores the wrong contents. The journal removes all guesswork.
- **Roll-back recovery (undo to the pre-operation state).** Requires keeping the old row state as well as the plan, and contradicts the user's intent once the commit succeeded. Roll-forward needs only the plan, and the final state is what the user asked for.
- **Filesystem transactions / renameat2 exchange tricks.** Platform-specific (Windows v1, macOS later), still not atomic across multiple files plus SQLite, and unnecessary once the journal exists.

## Consequences

- SQLite cannot defer composite (table-level) UNIQUE constraints, so `stickers` keeps immediate `UNIQUE(pack_id, position)` and `UNIQUE(pack_id, file_name)` guards, and the engine's commit transaction renumbers in two passes: first vacate every affected row's position and file name into a temp range, then assign the finals. The swap is still atomic — it just doesn't rely on deferred constraints.
- One journal row per pack (`pack_id` primary key) also serializes operations: a second operation on the same pack recovers the pending one first. The core assumes per-pack serialized calls; SPM-3's command wiring must not run concurrent operations on one pack.
- The `.spm-tmp-` prefix is reserved: dot-prefixed temps never sort into the `001.png…` sequence the owner drags into @Stickers, and the app never treats them as stickers.
- Recovery is part of opening a pack, so an interrupted operation is invisible to the user except as a brief repair on next open; desync detection then reports only genuine external desync (Missing), never false Missing from our own half-finished renames.
- Orphan empty pack folders (crash before create-commit) are the accepted residue: they hold no stickers, are ignored by the app, and are not reconstructed into packs; a later pack with that Short Name adopts an *empty* folder, while a non-empty folder (e.g. left by a delete that could not remove it) is never absorbed — auto-derivation skips past it and a typed name is refused. Deletion only ever removes folders whose stored names pass Short Name validation (no separators, dots, or reserved names), so a corrupted row cannot turn into a recursive delete of the Library.
- Opening a pack (and every operation on it) recreates the pack folder if it was deleted outside the app; its stickers then read as Missing and can be replaced (no reconstruction).
- A plan whose target name is occupied by a file the plan does not vacate is refused before the commit, so the roll-forward never meets a foreign file it did not expect. A pending folder rename's old name counts as a taken Short Name, so no new pack can adopt a folder that still holds the renamed pack's files.
- Crash safety is unit-tested by fault injection at the phase boundaries (after commit, after phase 1, mid phase 2, before journal cleanup): the test aborts the engine at each point, runs recovery, and asserts DB rows, filenames, and folder contents agree.

## Amendment 2026-11-25 (SPM-25): the Pack list runs recovery and detection too

The Pack list's rows report each pack's Missing count, so showing the list runs, for EVERY pack, exactly what opening it runs: recovery (a pending folder rename, then a pending rename plan) first, then the presence check, remembered in the same memo. One code path (`desync::build_view`), not a second presence check. Without the recovery step a pack with an interrupted rename would read as falsely Missing on the list, the very case the Consequences above rule out. A pack whose recovery fails (for example both folders of a pending rename exist) is reported on its own row and does not fail the list. Still never on app start: the app opens in the Editor, and the list runs only when shown. The earlier idea of a one-time check at startup is not used; it would contradict SPEC §4.
