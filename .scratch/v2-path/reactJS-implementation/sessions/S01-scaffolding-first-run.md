## Goal

React 19 becomes a working build-time citizen (deps, types, `jsx: react-jsx`,
plugin-react) with zero bytes of CSS/HTML/test/Rust change; the first-run view
(`src/views/first-run.ts`, 100 lines) is hand-ported to a React component mounted into
the existing `#app` shell via a root-tracking `mountView()` helper in
`src/react/mount.ts` that enforces "React roots never outlive their view" for view
switches and re-boots; licence notices gain react, react-dom and scheduler; the converted view passes
its Windows check. At session end the app behaves identically to today from the owner's
mouse-and-screen perspective, with `bun run dev` gaining Fast Refresh on the new `.tsx`.

## Work plan

Ordered build sequence. WP1 → WP4 per the phase file; the natural mid-session
checkpoint is the end of step 7 (WP2).

**WP1: Tooling scaffold + notices**

1. `bun add react@^19 react-dom@^19` and `bun add -d @types/react@^19
   @types/react-dom@^19 @vitejs/plugin-react@^5`. Exactly these five packages — no
   Tailwind, shadcn, eslint/prettier, react-testing-library.
2. `tsconfig.json`: add `"jsx": "react-jsx"` to compilerOptions. This is the ONLY
   compilerOptions change — do not touch strictness flags (`strict`,
   `noUnusedLocals`, `noUnusedParameters` stay; a stray unused import in the new tsx
   will fail `bun run build`, which is the intended catch).
3. `vite.config.ts`: `import react from "@vitejs/plugin-react";` and
   `plugins: [react()]` at top level of the config. Keep the existing `server`/`build`
   blocks (port 5173 strictPort, src-tauri watch ignore, es2022 target) untouched.
4. `bun run licenses` immediately (risk 1: run it now, not at the end). It regenerates
   `src-tauri/licenses/THIRD-PARTY-NOTICES.txt`. `runtimePackages()` (licenses.mjs:109)
   walks `dependencies` recursively, so react-dom pulls in its one runtime dependency,
   `scheduler`: the npm section should gain exactly three new MIT entries (react,
   react-dom, scheduler). If the closure surprises (a package with no license file),
   the fix is one line in `BORROWED_LICENSE_FILES` in `scripts/licenses.mjs`.
5. **WP1 checkpoint**: `bun install` clean; `bun run build` passes on the unchanged
   source tree; `bun test` passes (25 files); `git status` shows only package.json,
   bun.lock, tsconfig.json, vite.config.ts, THIRD-PARTY-NOTICES.txt;
   `git diff --stat <session base> -- 'src/**/*.css'` empty (plan.md › Session protocol step 3); the notices diff is exactly three
   new MIT entries (react, react-dom, scheduler). If any of this fails, stop and fix
   before WP2 — everything after depends on a green baseline.

**WP2: mountView() helper + shell hook**

6. Create `src/react/mount.ts`. Contract (plan.md binding contract #1, Phase 2 will
   extend it into a heterogeneous registry — do not build that registry speculatively):
   - Module-level `const roots = new Map<string, { container: HTMLElement; root: Root }>()`
     — the container is stored so "still mounted on this container" is answerable.
   - `mountView(container: HTMLElement, id: string, element: ReactElement): void` —
     if `roots` has an entry for `id` whose stored `container` is this container,
     re-render `element` into the existing root (fresh props on re-boot); otherwise
     unmount and drop every tracked root, then `createRoot(container)` +
     `render(element)` and store `{ container, root }` under `id`.
   - `unmountViews(): void` — unmount every tracked root and clear the map. Never
     called from inside a React render or commit (plan.md contract #1); its S01
     callers are main.ts's `boot()` branches and shell.ts's el() `show()`.
   - No `<StrictMode>` anywhere in `src/` (plan.md contract #3 — double-invoked effects
     would churn Konva later; the first-run pilot is unaffected but the rule starts
     here).
7. `src/shell.ts`: in `show()` (shell.ts:80), add `unmountViews()` immediately before
   `clear(content)` (shell.ts:82) — so the "React roots never outlive their view"
   invariant holds from day one even though no shell view is React yet. This is the
   only shell.ts touch; additive (one import, one call).
   **End-of-WP2 mid-session checkpoint**: `bun run build` passes; booting with a
   configured Library produces a DOM tree equivalent to today's shell render. main.ts
   is not touched yet (step 9).

**WP3: First-run pilot conversion**

8. Delete `src/views/first-run.ts`; create `src/views/first-run.tsx`. Hand-port — no
   codemod (plan.md hard constraint). The component is the named export `FirstRun`,
   takes `{ onReady: () => void }` and mirrors the deleted file's DOM exactly:
   - State: `chosenPath: string | null` (useState, init null), `userChose` (useState,
     init false) with a `userChoseRef` mirror (or a functional-setState bail — either
     satisfies the phase requirement) so the effect guard reads *current* state at
     resolution time, `message: string` (init `""`), `busy: boolean` (init false), and
     a state for the path display text (init `"Resolving default…"`) updated at the
     exact three points the original mutated `pathDisplay.textContent`.
   - Create button disabled state: one `createDisabled` state (init `true`) written at
     exactly today's points — `false` when the default resolves (first-run.ts:94), when
     a folder is picked (:32) and when `createLibrary` fails (:45); `true` when a create
     starts (:38). Not a derived `!chosenPath || busy`: today picking a folder while a
     create is in flight re-enables Create Library (:32 runs regardless of :38), and
     the port keeps that.
   - Default-resolution race guard → `useEffect(..., [])`: resolve
     `getDefaultLibraryPath()`; on success, if the user chose meanwhile, return — else
     set `chosenPath`, set the path display and set `createDisabled` false; on failure,
     if the user chose meanwhile, return — else set the path display to
     `"No default available — choose a folder."` and route `errorMessage(err)` into
     message state. The guard must read current state at resolution time, not the
     value captured at mount — naive porting here is the one regression class
     (phase risk 3; Windows-only timing means the Linux box may not reproduce it).
   - Choose-folder handler — `withMessage` cannot be reused (it mutates a `<p>` React
     owns); reimplement its contract inline (`src/ui.ts:43`: clear message first, run,
     route any error into it): clear message state, `await pickFolder(chosenPath ??
     undefined)`, return on `null` (user cancelled — change nothing), else set
     `chosenPath`, set `userChose` + ref, set the path display to the folder.
     `withMessage` stays untouched in ui.ts for un-migrated views (settings.ts,
     editor.ts, pack-view.ts still use it).
   - Create handler: if no `chosenPath` return; set `createDisabled` true (the
     original's `createBtn.disabled = true` during `createLibrary`); clear message; on
     success `await createLibrary(chosenPath)` then `onReady()`; on failure set message
     state and set `createDisabled` false (re-enable).
   - JSX tree, class names identical to the deleted file: `div.first-run` >
     `h1` "Welcome to Stickerpack Maker", `p` (the "keeps every pack and sticker
     file in a Library…" intro), `div.card` > `label.field-label` "Library folder",
     `code.path` (the display state), `div.actions` > `button.secondary`
     "Choose folder…" + `button.primary` "Create Library" (disabled), `p.message` with
     `role="alert"`, then `p.muted` "You can re-point at another Library or create a
     fresh one later in Settings." No new aria/role attributes (UI-audience rule);
     the existing `role="alert"` stays.
9. `src/main.ts` `boot()` rewiring — the one main.ts edit, made now that both
   `src/react/mount.ts` and `src/views/first-run.tsx` exist (main.ts stays `.ts` — it
   is orchestration, not markup; use `createElement`, not JSX, so no rename is needed
   and `index.html`'s `/src/main.ts` module script keeps working):
   - Imports: replace `import { renderFirstRun } from "./views/first-run"` (main.ts:7)
     with `import { FirstRun } from "./views/first-run"` (resolves to the `.tsx`); add
     `import { createElement } from "react"` and
     `import { mountView, unmountViews } from "./react/mount"`. Every import is used,
     so `noUnusedLocals` stays green.
   - `unconfigured` branch (main.ts:24): replace `renderFirstRun(root, () => void boot())`
     with `mountView(root, "first-run", createElement(FirstRun, { onReady: () => void boot() }))`.
   - `ready`/`invalid` branch: call `unmountViews()` immediately before
     `renderShell(root, state, ...)` (main.ts:30) — after the `applyEmojiStyle` await, so
     the old screen stays up until its replacement is drawn, as today.
   - `catch` branch: call `unmountViews()` before `root.replaceChildren(...)`
     (main.ts:33) so a live root cannot sit over a detached node (phase risk 2).
   - The re-boot callback still stops at this boundary: shell and its views remain
     opaque `el()` renderers. No keyed-generation Library invalidation (Phase 2+).
   `bun run build` is first expected green again after this step (step 8 removes the
   `renderFirstRun` export main.ts still imports until here).
10. Run the dev-time "no `createRoot` twice on the same container" check (temporarily
    log in mount.ts) across createLibrary → onReady → re-boot, and the boot error
    path (force `getAppState` to throw once) for a live root over a detached node;
    then remove the instrumentation.
11. **WP3 checkpoint**: build + tests pass; rendered DOM for the unconfigured state

## Owner / Windows checklist

Reach the `unconfigured` state by removing/renaming `config.json` in the app-config
dir for `com.stickerpackmaker.desktop`. Then:

1. "Resolving default…" appears, then resolves to Documents\Stickerpack Library with
   Create Library enabled.
2. Choose folder… → cancel leaves everything as it was.
3. Relaunch to the unconfigured state and click Choose folder… at once, while
   "Resolving default…" still shows (WP3 branch (2), the race); pick a different
   folder. After the default would have resolved, the path still shows the pick, and
   Create Library uses it. If the default always resolves before the dialog opens, note
   it — the race is then unexercisable on this box, and the pick-then-create half still
   counts.
4. Create against an unwritable path shows the error and re-enables Create Library.
5. Successful create lands in the Editor with the shell fully functional (proving the
   clean unmount of the first-run root).
6. One `bun run dev` pass to see Fast Refresh on the tsx (today every edit is a full
   reload — this phase's one dev-workflow payoff).

## Risks and fallbacks

1. Licence-closure surprise → run `bun run licenses` immediately in WP1 (step 4);
   fix is one BORROWED_LICENSE_FILES line in scripts/licenses.mjs.
2. Boot error path leaks a root → named review item; `unmountViews()` in the catch
   branch; dev-time instrumentation to confirm (step 10).
3. Race guard ported wrong (captured state instead of current) → WP3 exit criterion
   (2) + review item; one-line-mistake class; the userChose-ref (or functional bail)
   is the required shape.
4. `tsc --noEmit` widening: a stray unused import in the tsx fails the build — caught
   by `bun run build`, not the owner.
5. Windows-only timing: the race may not reproduce on a Linux dev box; Windows check
   checklist items 1 and 3 carry it; the view counts as converted only after the
   Windows check.
6. Scope creep via "while we're here" → the "Deliberately out of scope" lists are the
   review's scope fence.

Overrun fallback: if WP3 fidelity work overruns, S01 lands WP1+WP2 only and WP3 (the
pilot plus the step-9 main.ts wiring) moves to the opening of S02 as its step 0 —
S02's Preconditions then hold by explicit hand-off, not silently; first-run never ships
half-converted. Do not land a half-fidelity pilot to save the session: a wrong race
guard is worse than a slipped session.
